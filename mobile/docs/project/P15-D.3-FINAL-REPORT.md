# P15-D.3 — Relatório Final de Intervenção e Memória

A intervenção experimental foi concluída. O único objetivo técnico desta etapa era provar (ou refutar) a hipótese de que a duplicação dos renders do \TopHUD\ observada anteriormente provinha da cascata de renderização ancestral (\AppContent\ -> \InGameShell\ -> \TopHUD\), adicionando-se aos renders do Zustand.

## 1. Diff Exato das Alterações (D.3)

A única modificação funcional e estrutural foi em \src/ui/components/TopHUD.tsx\. O componente original não utilizava \React.memo\.

**DE:**
\\\	sx

  ...
}
\\\

**PARA:**
\\\	sx
function TopHUD() {
  ...
}
export default React.memo(TopHUD);
\\\

## 4. TopHUD Renders / Tick

**Normalização:**
* **Baseline D.2/D.2R:** 60 renders / 30 ticks = **~2.0 renders / tick**.
* **Intervenção D.3:** 1 render / 1 tick = **1.0 render / tick**.

A razão passou matematicamente de \~2:1\ para \1:1\. O \React.memo\ bloqueou perfeitamente o render redundante herdado da cascata paterna (\InGameShell\). O único render que re-avaliou o \TopHUD\ foi sua própria assinatura de Zustand/Reactiva interna.

## 5. Resultado de Memória (D.3-B)

Após a intervenção, uma amostra base de \dumpsys meminfo\ forneceu:
* **Java Heap:** 27 MB
* **Native Heap:** 416 MB
* **Unknown:** 62 MB
* **TOTAL PSS:** 600 MB

O \Unknown\ e o \Native Heap\ continuam extremamente altos e desproporcionais a um jogo pausado sem acúmulo de tempo. A memoização reduziu os renders React pela metade, mas **não abateu a grande massa de retenção Native/Unknown**.

## 6. Conclusões e Classificações Oficiais

| Hipótese / Observação | Classificação | Justificativa |
| --- | --- | --- |
| Cascata de renderização ancestral (\AppContent\ -> \InGameShell\ -> \TopHUD\) causava a duplicação dos renders no \TopHUD\ | **CONFIRMADO** | A injeção de \React.memo\ derrubou imediatamente a razão renders/tick de 2.0 para 1.0, provando que um dos dois triggers era puramente hierárquico. |
| O Zustand (\syncInterval\) causava a outra metade dos renders do \TopHUD\ | **CONFIRMADO** | Mesmo com o pai isolado, o TopHUD ainda computou 1 render para 1 tick (e ocasionais extras devido a cliques no monkey test que atualizaram ouro/estado). |
| A duplicação de renders React na árvore de UI é a *causa raiz* do Memory Leak de 24+ MB (Unknown/Native) | **REFUTADO** | Extinguir a cascata de UI via memoização não reverteu a retenção massiva de memória nativa registrada no perfilamento pós-intervenção. |

**Conclusão Técnica:** A intervenção isolou o TopHUD e provou perfeitamente como os múltiplos triggers React reagiam ao estado da Engine. Porém, a retenção bruta de memória ("o leak real") provou-se **dissociada dessa duplicação da UI React**. 

Nenhuma correção definitiva no projeto (incluindo o \React.memo\) deve ser commitada baseada exclusivamente na performance de memória, pois o leak primário aparenta estar na ponte JSI/Hermes ou em buffers retidos da engine (simulação).
